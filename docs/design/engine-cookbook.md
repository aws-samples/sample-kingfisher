## 0. One-sentence conclusion

**Consolidate "engine engineering knowledge" into a platform-level Cookbook: maintained in one place, reused in many, retrieved on demand, guiding before generation and validating after generation.**
It is the **shared foundation** of every AI code-generation capability (it belongs to no single module); a read-only embedded base ships with the platform, administrators can extend it with enterprise patterns,
and retrieval is deterministic by `engine + capability` (only the relevant recipes are fed to the model, which controls token cost).

**Honest statement of boundaries (new in revision 2, see section 4.3)**: `retrieve` (guidance before generation) applies to **all** codegen outlets;
`guard` (validation / correction after generation) can perform reliable mechanical correction only for **declarative SQL** (Redshift / Athena / Flink SQL);
for **imperative code** (PySpark / Python for Glue / EMR) it only emits **warn-level pattern hints and performs no regex rewriting** (rewriting is prone to collateral damage, see section 10, finding B).

---

## 1. Why this is needed (the essence of the problem)

**Symptom**: the Redshift SQL generated by Copilot used `CREATE TABLE IF NOT EXISTS ... AS` (PostgreSQL dialect), and Redshift rejected it.

**Essence (3 deeper problems)**:
1. **Knowledge is scattered and relies on the model's "memory"**: engine dialects, function usage and version differences are scattered across the model's training knowledge — unreliable, uncontrollable,
   and prone to hallucination. The platform has no single source of truth of "verified engineering patterns".
2. **Privatized capability**: the recipes created by the root-cause fix serve only Copilot planning. But the AI-generated SQL / code of **batch development, stream development and Ask-Your-Data**
   faces **exactly the same** dialect / version pitfalls, yet each outlet fights alone and steps into the same traps again.
3. **Risk of runaway cost**: if all knowledge of all engines were stuffed into the prompt of every model call, token cost would grow linearly with the knowledge base,
   and most of the irrelevant content would be pure waste.

**Goal**: consolidate verified engineering knowledge in one place → share it across all codegen outlets → retrieve on demand (control tokens) → guarantee generation quality at the source.

So phases 3 through 5 **instrument these existing endpoints with retrieve + guard**; they do not build new generators (see section 8).

## 3. Retrieval mechanism (the core of token control, the top concern)

### 3.1 This phase: deterministic tag / engine retrieval (zero infra, zero extra cost, controllable)
```text
retrieve(engine, opts?: { capability?, keywords?, topK? }): CookbookSlice
```
- **First filter: engine**. Load only the knowledge of the target engine (computing Redshift ROI does not load Flink / EMR recipes).
- **Second filter: capability / keywords scoring and ranking**. Score by number of tag hits + keyword matches in title / whenToUse, take the topK.
  (Computing ROI → recipes tagged aggregate / roi come first; CDC / upsert recipes are not returned.)
- **Always injected: the error-level hard dialect rules of that engine** (small in size, must always be carried, prevents fatal syntax errors).
- The returned volume is controllable: dialect rules (all, but small) + topK relevant recipes (default K=3). **Tokens are spent only on relevant content.**

> - **⚠ Revision 2 correction of the current state (see section 10, finding E)**: the description above is the **target state**. The current state of the unified-Copilot prototype at `registry.ts:27` is
> - **pure substring `includes` filtering with no scoring, no ranking and no topK**; `capability` is a free-form string.
> - **Phase 1 must upgrade "substring filtering" to "scoring + topK truncation"; otherwise the cost benefit of section 3.3 does not hold** —
>   this item is **pulled out of "migration with unchanged behavior" and implemented separately** (it is the core value of this module and does not count as a regression).

### 3.2 Future: vector retrieval / RAG (an upgrade path that does not block this phase)
Once the knowledge base grows large (hundreds of recipes), tag-match recall may become insufficient → upgrade to embeddings-based semantic retrieval.

**The interface does not change** (the `retrieve` signature is stable); only the internal implementation is swapped → tags now, vectors later, invisible to callers.

### 3.3 Cost comparison (why it is designed this way)

| Approach | Tokens injected per codegen call | As the knowledge base grows |
|---|---|---|
| Inject all knowledge of all engines | Large and ever-growing | ❌ Linear growth, wasteful |
| **Retrieve by engine + capability topK** | Small and stable | ✅ Only the relevant part grows |

### 3.4 Retrieval performance: in-process cache (new in revision 2, see section 10, finding F)
The system-embedded recipes (seed) are code constants, zero IO. Administrator-defined dynamic recipes (store) live in DynamoDB —
the prototype issues one DynamoDB Query on every `getCookbook` call with no cache. This does not matter for low-frequency codegen, but **high-frequency GenBI questions that retrieve on every question
would accumulate read latency / cost**. Phase 1 adds an **in-process TTL cache** to store reads (for example 60 s, refetched on expiry); `retrieve` hits the cache first.
Cache-invalidation fallback: actively bust the cache after an administrator adds or deletes a recipe (or accept eventual consistency within ≤ TTL).

## 4. The two unified capabilities (every codegen outlet goes through them)

### 4.1 Before generation: `retrieve(engine, intent)` → guide the model
Before calling the model, the codegen outlet retrieves the dialect rules + patterns for "this engine, this intent" and injects them into the prompt / tools.
The model writes according to verified patterns → **correct at the source**. **retrieve applies to every outlet (including PySpark)** — pattern guidance is equally effective for imperative code.

### 4.2 After generation: `guard(engine, code)` → validate + correct
Before persisting / executing, validate with **the same dialect rules**. **Shared source of truth**: retrieve and guard consume **the same set of DialectRule** —
a rule is changed in one place and both capabilities pick it up together. The guard has **3 production-grade hard requirements** (new in revision 2; the prototype met none of them, see section 10):

- **(a) Lexical safety (mandatory, section 10 finding A, a fatal latent defect)**: antiPattern matching and fix rewriting **must not be applied directly to the raw text**.
  SQL comments (`--`, `/* */`), string literals (`'...'`) and quoted identifiers (`"..."`) **must be masked first**;
  hits are determined and rewrite positions located on the masked text, then restored. Otherwise a legal string such as `WHERE note='CREATE TABLE IF NOT EXISTS ...'`
  would be **corrupted by the fix, damaging user data** (the backtick→double-quote rule has the same problem). Phase 1 delivers the `maskSqlLiterals` utility + false-positive tests.
- **(b) Idempotence / fixed point (mandatory, section 10 finding D)**: multiple fix rules must **iterate to a fixed point** (fixpoint, with a maximum-round cap against infinite loops),
  and every fix must satisfy "after fixing, its own antiPattern no longer matches". The prototype is a single pass that is stable only because "the rule contents happen not to interact" —
  this breaks once administrators / future work extend the rules. Phase 1 changes it to fixpoint iteration + rule-orthogonality tests.
- **(c) Violation-handling policy (mandatory, section 10 finding G)**: guard returns `{ script, fixed[], violations[] }`.
  - `fixed` (auto-corrected): **written to the audit log + echoed to the user** ("the AI wrote X, automatically corrected to Y"); it must not be swallowed silently.
  - `violations` (error level without a fix, for example referencing a non-existent function): **block persisting / execution** and report the error explicitly,
    rather than persisting a piece of code that is guaranteed to fail. Whether a user may "force-override after being informed" is decision point ⑥ in section 9.

### 4.3 Applicability matrix (new in revision 2; honest boundaries, see section 10, finding B)
The guard's mechanical correction is based on "regex antiPattern + fix rewrite", and that mechanism is **effective only for the surface syntax of declarative SQL**.
For imperative code (PySpark imports / DataFrame chains / boto3 / `job.commit()`) **regexes cannot reason reliably about semantics**, and forcing a fix would cause collateral damage.

| Outlet | Output | retrieve (before generation) | guard (after generation) |
|---|---|---|---|
| Copilot `redshift-sql` step | Redshift SQL | ✅ | ✅ corrects |
| Copilot `glue` / `emr` step | PySpark | ✅ | ⚠ warn-level hints only, **no fix** |
| Batch ETL (targetType=redshift) | Redshift SQL | ✅ | ✅ corrects |
| Batch ETL (targetType=glue) | PySpark | ✅ | ⚠ warn-level hints only, **no fix** |
| Realtime Flink | Flink SQL (declarative) | ✅ | ✅ corrects (Flink dialect rules must be added first) |
| Ask-Your-Data GenBI | Redshift / Athena SQL | ✅ | ✅ corrects |

**Conclusion**: for PySpark outlets, quality assurance relies on **retrieve guidance before generation** (supplying the right patterns) + execution-time error feedback,
**not on guard regex rewriting**. The design no longer claims that "guard covers every outlet".

## 5. Data model (extended from the unified Copilot's recipes/types.ts)

```ts
type CookbookEngine = "redshift" | "s3tables" | "glue" | "emr" | "flink" | "athena" | ...;

interface DialectRule {           // 引擎方言硬规则(retrieve 注入 + guard 校验的共享源)
  id; engine; title; rule;        // rule: 给 AI 看的约束文案
  antiPattern?: RegExp;           // 命中=违规(guard 检测,须作用于 mask 后文本)
  fix?: (code) => code;           // 可机械纠正的修法(仅声明式 SQL 配 fix;命令式引擎只给 warn 文案)
  severity: "error" | "warn";
  engineVersion?: string;         // 【新增】适用版本(如 "glue>=5.0" / "redshift-serverless"),空=通用
  target?: "sql" | "code";        // 【v2 新增】声明该规则针对声明式SQL还是命令式代码;code 型禁配 antiPattern+fix
}

interface Recipe {                // 验证过的代码范式
  id; engine; capability; title; whenToUse;
  template; dialectNotes; tags;
  engineVersion?: string;         // 【新增】范式适用版本
  verifiedAt?: string;            // 【新增】验证时间戳(证明"跑通过",非凭记忆)
  source: "system" | "admin";     // 内嵌只读 / 管理员扩展
}
```text

**Controlled capability vocabulary (new in revision 2, see section 10, finding E)**: `capability` stays a string so that flexibility is not broken, but a
**controlled vocabulary + alias mapping** is maintained (for example `aggregate|rollup` and the localized Chinese alias all normalize to `aggregate`); retrieve normalizes during scoring,
and an administrator adding a recipe with an unknown capability gets a **soft warning** (not blocked). This keeps retrieval hits stable without locking out extension.

**Version differences (a stated concern)**: the `engineVersion` field annotates them explicitly. The same capability may have several recipes for different versions,
and retrieve prefers the one matching the platform's current engine version (for example Glue 5.1). **"All versions mixed together for the model to guess" is not an option.**
> ⚠ Dependency: preferring by `engineVersion` requires a source for "the platform's current engine version" (decision point ⑤ in section 9). **Until the version source is settled,
> `engineVersion` is display-only annotation and does not participate in preference filtering**, so that it does not become a dead field.

## 6. Content governance (red line: only administrators may add, and only verified content is admitted)

1. **System-embedded recipes (seed)**: embedded in code, shipped with the platform, read-only. Adding a system recipe = a developer PR + redeployment.
   **Must be verified before admission** (as was done for the unified-Copilot root-cause fix, which really ran Redshift to confirm the CTAS behavior) — never pour the model's memory / hallucinations
   straight in (that would encode errors into the platform, which is more dangerous). An admitted recipe must carry `verifiedAt` + a description of how it was verified.
2. **Administrator-defined dynamic recipes (store)**: DynamoDB; `isPlatformAdmin` can add and delete, ordinary users read only. This is the entry point for consolidating enterprise-specific patterns.
3. **Hard dialect rules come only from the system embedding**: a dialect is an objective fact of the engine and is maintained by the platform; administrators can add "patterns (Recipe)" but
   **cannot change "dialect rules (DialectRule)"** (this prevents a misconfiguration from breaking the guard validation layer — and it is the precondition that lets the guard rewrite automatically at all).

### 6.1 Internationalization (i18n) constraint — a platform-wide hard constraint for anything that touches the frontend

The platform is bilingual Chinese / English (the i18n module: "the Chinese string is the key" + antd integration). For the UI parts of the Cookbook, **all user-visible text must go through `useT()`**:
- **Phase 1 (pure library foundation)**: no UI → no i18n need (recipe template / rule texts are **engineering code / engine facts**, not UI text, and are not translated).
- **The CookbookLibrary management page** (lifted from RecipeLibrary): table headers, buttons, system / administrator badges, add / delete form labels and placeholders → all through `useT()`.
- **The guard echo in each codegen outlet** (for example "the AI wrote X, automatically corrected to Y", "this SQL violates <rule> and was blocked"):
  the **framework text** of the message goes through `useT()`; the embedded **rule title / SQL fragment** is data and is not translated (following the i18n module's "business data is not translated" principle).
- **Not translated**: recipe template (code), DialectRule.rule (engine constraints shown to the AI, not end-user UI), the canonical capability words (retrieval keys).

## 7. Directory structure (platform level, self-contained in one directory)

```
platform/src/lib/cookbook/          # platform level (lifted + generalized from lib/copilot/recipes)
  types.ts            # DialectRule / Recipe / CookbookSlice + engineVersion / verifiedAt / target
  retrieve.ts         # [core] retrieve(engine, opts) deterministic retrieval (engine filter → capability scoring → topK)
  guard.ts            # guard(engine, code) validation / correction (lexical mask → fixpoint iteration → returns fixed / violations)
  mask.ts             # [new in revision 2] maskSqlLiterals: strips comments / strings / quoted identifiers so the guard can match safely
  registry.ts         # merges system-embedded (seed) + administrator dynamic (store), with an in-process TTL cache
  capability-vocab.ts # [new in revision 2] controlled capability vocabulary + alias normalization
  seed/               # system-embedded recipes (read-only base), one file per engine
    redshift.ts / s3tables.ts / glue.ts / emr.ts / flink.ts / athena.ts / index.ts
  store.ts            # administrator dynamic recipes (DynamoDB bgp-cookbook-recipes)
platform/src/app/api/cookbook/
  route.ts            # GET list recipes (readable by everyone) / POST add (admin only)
  [recipeId]/route.ts # DELETE (admin only)
platform/src/components/cookbook/
  CookbookLibrary.tsx # recipe management page (lifted from RecipeLibrary, mountable in several places)
```

**Migration**: the contents of the unified Copilot's `lib/copilot/recipes/*` move into `lib/cookbook/`, and the Copilot planner switches to calling `cookbook.retrieve/guard`.
Copilot-side behavior stays unchanged (smooth migration; contract-guard protects against regression).

> Every insertion point has been verified to file:line.

| Phase | Content | Key insertion point / notes |
|---|---|---|
| **Phase 1** | Lift the `lib/cookbook/` foundation: retrieve (scoring + topK) + guard (mask + fixpoint + violation handling) + cache + migrate Copilot | Fulfills the 3 hard requirements of sections 3.1 / 4; Copilot behavior unchanged (contract-guard protects against regression) |
| **Phase 2** | Expand the system recipes (cover high-frequency capabilities + version annotations) + every recipe verified with `verifiedAt` | Solves "too few recipes"; the high-frequency scenarios must be listed (section 9, ③) |

| **Phase 5b** | 🔴 **Change the AgentCore remote Runtime image**: make SQL generated inside the container go through the guard too, eliminating the blind spot (decision ⑦) | **Touches the production core path, under a red line — see section 8.1** |

> GenBI already has an independent read-only safety guard (`sql-guard.ts` rejects non-SELECT statements / limits rows); the cookbook guard **sits alongside it and does not replace it** —
> the former handles "read-only safety", the latter "dialect correctness".

### 8.1 Red line for phase 5b: changing the AgentCore remote image (mandated on 2026-07-18)

> The mandate, verbatim: "The runtime image has to be changed; you need to verify it thoroughly, there must be no problems, you need to verify several rounds, and it must not affect any other feature. This is a red line."

Changing the GenBI AgentCore remote Runtime image = **touching a production AI capability that is already live and has passed third-party verification**. All of the following must be satisfied; if any one is missing, do not proceed:

1. **Tag before the change** as a rollback anchor (`pre-genbi-guard-runtime`), following the engineering discipline `tag-before-big-changes`.
2. **Zero functional regression**: the image change **only** adds one guard validation / correction step "after the remote SQL is generated, before it is executed", and **does not touch** any existing GenBI path —
   table selection (retrieval), the read-only guard, asynchronous submit + poll, heartbeat / claiming, result persistence. Contract snapshot → verify all green.
3. **Multiple independent verification rounds** (not just once): ① before changing the image, verify the guard logic thoroughly in-process (phase 5a);
   ② after changing the remote image, first run **multiple sets of real questions** in a temporary environment (dialect-prone scenarios + normal scenarios + edge cases) to confirm that it corrects errors without collateral damage;
   ③ verify end to end with a headless browser on the real `/genbi` page (look at the page result, not at the API); ④ confirm that the AgentCore fallback to the in-process path still works.
4. **No impact on other features**: the AgentCore platform standard is "an independent Gateway + Runtime + Memory per AI capability" ([AgentCore standard](./agentcore-standard.md));
   this change **rebuilds only the single GenBI Runtime image** and does not touch the images or wiring of the network advisor / parameter advisor / Copilot or any other AgentCore capability.
   Deployment follows the existing GenBI image release procedure (two deployment passes + `--provenance=false` to avoid the attestation pitfall, see the GenBI AgentCore deployment note).
5. **Rollback-able**: keep the previous image tag / TaskDef revision; if verification falls short, roll back immediately and never go live with a known defect.

**If any verification round finds that the guard causes collateral damage or affects an existing path → stop phase 5b, fall back to "guard in-process only + document the remote blind spot",
and downgrade the remote image change to a separate follow-up task** — better to leave a documented, known blind spot than to risk polluting production GenBI.
