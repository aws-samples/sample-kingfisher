# Execution Role Binding

Status: implemented. Code lives under `platform/src/lib/execution-role/` and `platform/src/components/exec-roles/`.

Related: [Long-running operations](long-running-operations.md), [Supported versions](../supported-versions.md).

## 1. Summary

- Every job that runs on an AWS compute service can be bound to an IAM execution role chosen by the user.
- The rule is parity with the AWS console: any role in the account that the service can assume is a valid choice.
- The platform default role of the region and roles generated by the role advisor remain available.
- The role field is a grouped, searchable dropdown with an in-page refresh button and a manual ARN fallback.
- Permissions are measured at save time against the job's real reference surface; gaps block the save with a reason list.
- The stored field name and its empty-means-default semantics are unchanged, so existing jobs keep working.

## 2. Problem

### 2.1 What the pages promised

- Offline compute (Glue and EMR Serverless), data sync and real-time compute each had a free-text "execution role ARN" field.
- The help text promised "or enter a custom least-privilege role".

### 2.2 What actually happened

| Layer | Fact | Consequence |
|---|---|---|
| Platform task role | `iam:PassRole` allowed only platform-named roles and advisor roles | Any customer-created role failed at `CreateJob`, `StartJobRun` or `CreateApplication` |
| Region platform Glue role | S3 access limited to the region's data-lake and scripts buckets | Falling back to it, a job reading a customer bucket failed at launch with 403 |
| Preflight | Only on the EMR path; only engine baseline resources; no trust check | Save succeeded, run failed, error text did not name the fix |
| Single author | ARN regex and "custom first, empty falls back" copied into four entry points | A fix in one place missed three others |

In one sentence: the UI claimed a capability without a carrier. The missing carriers were the IAM pass surface, a candidate source, and a save-time preflight.

## 3. Requirements

| # | Requirement |
|---|---|
| R1 | Glue jobs, EMR Serverless jobs, sync Glue jobs and Flink applications can bind any role the service can assume |
| R2 | The role field is a dropdown in three groups: platform default, advisor generated, custom; searchable; shows role names |
| R3 | A refresh button next to the dropdown reloads candidates without leaving the page |
| R4 | The platform task role can pass any role to the three services and can list, read and simulate any role |
| R5 | Preflight moves to save and start, measuring the job's actual reference surface; gaps reject with 400 and remedies |
| R6 | Field name `executionRoleArn` and empty-means-default are unchanged; old clients keep working |
| R7 | Multi-region: the default entry follows the place; custom roles are account-global; simulation carries the region |
| R8 | Friendly text: role names not ARNs, group titles explain the choice, results shown in place |

Out of scope: DMS and Redshift COPY roles are internal orchestration roles and are not user-selectable.

## 4. Parity with AWS

| Engine | Job type | Service principal the role must trust |
|---|---|---|
| `glue` | Offline compute Glue job, sync Glue job | `glue.amazonaws.com` |
| `emr` | Offline compute EMR Serverless job | `emr-serverless.amazonaws.com` |
| `flink` | Real-time compute Flink application | `kinesisanalytics.amazonaws.com` |

- The engine list is closed (`EXEC_ROLE_ENGINES`); an unknown engine is rejected with 400.
- A role is a candidate when its trust policy lists the engine's service principal, exactly like the console dropdown.
- No tag condition is required on customer roles; the security boundary is the service condition on `PassRole`.

## 5. IAM changes

A managed policy `ExecutionRoleBinding` is attached to the platform task role.

| Statement | Action | Resource | Condition |
|---|---|---|---|
| `PassAnyRoleToJobServices` | `iam:PassRole` | `role/*` | `iam:PassedToService` in the three principals above |
| `ListRolesForExecutionRolePicker` | `iam:ListRoles` | `*` | none |
| `ReadAndSimulateAnyExecutionRole` | `iam:GetRole`, `iam:SimulatePrincipalPolicy` | `role/*` | none |

- No `aws:RequestedRegion` condition: IAM is global and the condition would block legitimate calls.
- The existing narrower `PassRole` statements stay in place.
- The synth gate asserts that a `role/*` `PassRole` statement exists, carries the service condition, and names exactly these three services.
- The IAM call manifest lists the new calls; the deploy-time simulation gate verifies them against the task role.

## 6. Single author module

| File | Responsibility |
|---|---|
| `types.ts` | Closed engine list, service principal per engine, candidate and group types |
| `resolve.ts` | The only ARN regex; `resolveExecutionRoleArn({ custom, fallback, missingMessage })` returns `{ roleArn, isCustom }` |
| `trust.ts` | `trustsService(assumeRolePolicyDocument, service)` parses the URL-encoded trust policy |
| `candidates.ts` | `listExecutionRoleCandidates({ engine, targetId })` and `platformDefaultRoleArn(engine, targetId)` |
| `s3-uris.ts` | Extracts S3 URIs from job dependency fields and from `s3://` literals in scripts |
| `preflight.ts` | `preflightExecutionRole`, `preflightCustomRoleForTargets`, error response shaping |

- A ratchet test asserts the role ARN regex appears only in `resolve.ts`; eight earlier copies were removed.
- `resolveExecutionRoleArn` prefers a non-empty custom value, falls back to the platform default, and throws the caller's message when both are empty.

## 7. Candidate listing

1. Resolve the platform default role for the engine and place: home region from the environment, other regions from the execution-environment descriptor.
2. List all roles in the account with paginated `ListRoles` on the control-plane IAM client.
3. Classify each role.
4. Keep a non-platform role only if its trust policy includes the engine's service principal.
5. Return `{ groups: { platform[], advisor[], custom[] }, servicePrincipal, fetchedAt }`.

| Classification | Rule |
|---|---|
| `platform` | ARN equals the resolved platform default for this engine and place |
| `advisor` | Name starts with the role advisor prefix `bgp-job-role-` |
| excluded | Service-linked roles (path `/aws-service-role/`) |
| excluded | Internal platform roles: names starting with `BgpExecEnv-`, `Bgp...Stack-` or `bgp-` |
| `custom` | Everything else |

- The platform default is always listed, even if its name looks internal.
- Each candidate carries `arn`, `name`, `kind`, and optionally `createDate` and `description`.

## 8. Preflight by capability

### 8.1 What is checked

1. ARN shape.
2. Role existence (`GetRole`).
3. Trust policy includes the engine's service principal.
4. Permission simulation (`SimulatePrincipalPolicy`) over the job's actual reference surface.
5. Result in three states: complete, gaps, or unverifiable.

### 8.2 Reference surface per engine

| Engine | Probed resources |
|---|---|
| Glue | Engine baseline (log group, scripts bucket, data-lake bucket), each `--extra-py-files` and `--extra-jars` URI, each `s3://` literal in the script |
| EMR | Engine baseline (scripts bucket, data-lake bucket), each `s3://` literal in the script |
| Flink | Engine baseline (code bucket) |

- Every dependency URI adds two probes: `s3:GetObject` on the object and `s3:ListBucket` on the bucket, with statement id `JobDependencyRead`.
- The simulation carries `aws:RequestedRegion` equal to the place's region, so customer roles with region conditions are measured correctly.
- Only custom roles are measured; platform default roles are created by the infrastructure and are known to be complete.

### 8.3 Three states

| State | Meaning | Effect |
|---|---|---|
| complete | All probes allowed | Save and run proceed |
| gaps | At least one probe denied | Save or start rejected with 400 |
| unverifiable | `GetRole` or simulation itself failed (throttling, missing permission) | Save proceeds; the result is shown as "could not verify" |

Unverifiable does not block, because a broken preflight must not stop every job on the platform.

### 8.4 Rejection shape

```json
{ "success": false,
  "error": { "code": "VALIDATION_FAILED",
             "message": "<lines: action -> resource (decision) and why it is needed, then remedies>",
             "detail": { "reason": "exec-role-preflight", "engine": "glue", "roleArn": "<arn>",
                         "targetId": "<targetId>", "roleExists": true,
                         "gaps": [ { "sid": "JobDependencyRead", "action": "s3:GetObject",
                                     "resource": "arn:aws:s3:::<bucket>/<key>", "why": "...", "decision": "implicitDeny" } ],
                         "checked": 9 } } }
```

Remedies listed in the message:

- Grant the listed actions to the role.
- Use the role advisor to generate or complete a role.
- Move dependency libraries to the platform bucket through the page upload.
- Leave the field empty to use the platform default.
- When the trust policy is the problem: add the service as a trusted entity in IAM.

## 9. HTTP API

| Route | Purpose |
|---|---|
| `GET /api/exec-roles/candidates?engine=&targetId=` | Dropdown candidates for one engine and place |
| `POST /api/exec-roles/preflight` | "Check permissions" button; body `{ engine, targetId, roleArn, extraS3Uris?, scriptCode? }` |

| Status | Code | When |
|---|---|---|
| 401 | `UNAUTHENTICATED` | Not signed in |
| 400 | `VALIDATION_FAILED` | Engine not in the closed list; `targetId` missing; ARN shape invalid; `roleArn` empty on preflight |
| 409 | `CONFLICT` | Place binding rejected |
| 502 | `UPSTREAM_ERROR` | IAM read failed; for `AccessDenied` the message says to upgrade the platform or use manual ARN entry |

- Both routes require an explicit `targetId`; the home region is never assumed.
- The preflight route is a preview; save and start paths measure again on the server and do not trust the client.

## 10. Where the role is used

| Entry point | Behaviour |
|---|---|
| `lib/etl/job-service.ts` (`ensureGlueJob`) | Resolves the role; custom role is preflighted with dependency URIs and script literals before create or update |
| `app/api/etl-jobs` POST and PUT | Custom role preflighted per bound region before the row is written; on update only when role, dependencies, script or bindings changed |
| `lib/sync/start-run.ts` | Same for the sync Glue channel; gaps reject the start |
| `lib/realtime/flink-service.ts` and Flink routes | Engine `flink`; trust principal `kinesisanalytics.amazonaws.com`; preflight after place validation |
| `lib/engines/emr/provider.ts` and `schedule-fanout.ts` | Already preflighted; now through the single author; the scheduled fan-out gained the preflight |
| Workflow job node preparation | EMR nodes with a custom role are preflighted per region at publish |

### 10.1 Dependency uploads per region

- Uploading a dependency from the job page writes one copy per bound region into that region's scripts bucket under `glue-deps/<jobId>/<file>`.
- The response reports `uploaded { targetId: uri }` and fills the field with the first bound region's URI (home first).
- At submit time a platform-bucket URI under `glue-deps/` is rewritten to the submitting region's scripts bucket; customer bucket URIs are left untouched.

Behaviour:

- The first option is "Platform default role (recommended)" with an empty value.
- Groups are titled platform default, advisor generated, and custom; a hint under custom roles says the role must trust the service and must read the buckets the job depends on.

- A failed candidate load shows an alert, not a toast, and the manual toggle remains usable.
- The role advisor panel stays below the picker; a one-click creation selects the new role and refreshes the list.

Pages replaced: offline compute Glue job form, EMR job panel, sync task modal (Glue channel only; the DMS channel keeps its input), real-time compute page.

## 12. Multi-region behaviour

- The platform default entry is resolved per place: environment variables for the home region, descriptor fields for other regions.
- Custom roles are account-global and appear for every place.
- A job bound to several regions is preflighted once per region, each with that region's context.
- The picker requests candidates for the first bound region and shows a hint for multi-region jobs.

## 13. Compatibility and upgrade

- No new tables; no field renames; empty value semantics unchanged.
- New routes are additive; the four save and start routes gain one 400 case only when a custom role is set.
- Upgrade: redeploy the platform stack (new managed policy on the task role); execution regions and agents are unchanged.
- Rollback: the previous image shows the free-text field again; stored values remain valid.

## 14. Acceptance behaviour

Page-driven scenarios in a headless browser, with API and CLI reads as cross-checks:

1. A customer-created role trusting Glue is bound to a Glue job; save passes; run succeeds; the Glue job definition's role equals the ARN.
2. A dependency points at a customer bucket the role cannot read; save returns 400 naming `s3:GetObject` and the bucket; "check permissions" lists the same gap; after granting the permission and refreshing, save and run succeed, and the dependency is downloaded from the customer bucket.
3. A role created in IAM appears in the custom group after one in-page refresh, without a page reload.
4. An existing job saved without changes keeps an empty role field and shows "Platform default role" with the region's default name.
5. From a non-home region's view, the default entry is that region's role and the candidates request carries that region's `targetId`.
6. Uploading a dependency for a non-home job writes it to that region's scripts bucket and not to the home bucket.

Unit guards:

- Candidate grouping and trust-policy parsing.
- Resolver single author (ARN regex ratchet).
- URI extraction from dependency fields and scripts.
- Preflight extension: a missing object permission produces exactly one gap; a missing trust relationship rejects.
- Route status matrix (401 / 400 / 409 / 502).
- Component server render with the form-injected id.
- Four forms replaced and no free-text field returned, except the DMS channel.

Mutations: removing the service condition turns the synth gate red; removing a preflight call turns the wiring test red.

## 15. Risks and limits

- Accounts with more than a thousand roles make `ListRoles` slow; results are paginated and fetched only on open or refresh.
- Customer roles with region or other conditions are measured with the region context; anything unmeasurable is reported as unverifiable.
- `PassRole` on `role/*` is bounded by the three service principals; a tag condition can be added later if a security review requires it.

## 16. Known gaps

- Deleting a job while a run it just started is still in flight is not blocked by this design.
